# Finance 웹앱 구현 계획

기존 finance-cli 기능을 모바일과 PC의 웹브라우저에서도 제공한다. CLI와 에이전트 자동화는 계속 사용할 수 있으며, 웹앱은 같은 금융 프로필과 업무 기능을 이용한다. 기관별 업무 로직은 서버에서 관리하므로 해당 로직을 수정할 때 클라이언트를 다시 배포할 필요가 없다.

이 문서는 구현 계획이다. 현재 제공된 [UI 시안](../web/preview/README.md)은 가상 데이터로 동작하며 API와 실제 금융 기능은 연결되어 있지 않다. 구현은 아래 단계에 따라 진행한다.

여러 은행과 개인·개인사업자·법인을 지원할 때의 데이터 모델·인증 수단·세션·CLI 호환은 [업무 프로필과 기관 연결 설계](profiles-and-connections.md)를 따른다. 사용자 한 명이 여러 업무 프로필을 사용할 수 있으며, 프로필 아래에 기관 연결과 용도별 인증 수단을 둔다.

## 사용자 경험

- 상단 공통 바에 **업무 프로필의 이름·유형**을 항상 표시하고 개인·개인사업장·법인을 전환한다. 프로필은 탭별 표시 대상이며 서버 전역의 현재 대상이 아니다.
- 좌상단에서 **뱅킹·지로·세금**을 전환한다. 왼쪽 메뉴는 선택한 영역의 기능만 표시하고 프로필별로 각 영역의 마지막 화면을 유지한다.
- 모바일에서는 같은 영역 전환과 하단 주요 메뉴 3개·전체 메뉴를 사용한다. 모바일과 PC는 같은 API·작업·결과를 공유한다.
- **전체 작업 기록·연결 및 인증서·전체 기능과 지원 상태**는 공통 메뉴로 둔다.
- 뱅킹에서는 현재 프로필의 여러 은행 계좌를 모아 보고 기관 연결별로 필터링한다. 은행별 로그인 상태·조회 시각을 구별한다.
- 홈택스의 개인·사업장 대상은 현재 프로필의 기관 연결에 지정한다. 다른 사업장은 프로필을 전환해 이용하며 조회 결과·초안·진행 중인 작업에는 고정된 대상을 표시한다.
- 제공 예정인 미구현 기능은 숨기지 않고 **준비 중**으로 표시하며 비활성화한다. 서버에서도 해당 기능의 실행을 거절한다.
- 인증서 파일 관리와 운영 도구는 **서버에서 관리**로 구별한다. 미구현 기능과 같은 상태로 표시하지 않는다.

시안의 화면 구성·메뉴·색상·이체 및 계산서 확인 흐름을 구현 기준으로 삼는다. 시안의 예시 금액·계좌·기한·상태는 제품 데이터나 기본값으로 옮기지 않는다.

현재 시안에는 상단 업무 프로필과 여러 은행의 연결 관리가 아직 없다. 해당 부분은 프로필 설계에 맞춰 추가하고, 시안의 홈택스 내부 개인/사업장 선택은 공통 프로필 전환으로 통합한다.

## 기능과 CLI 연결

구현 범위의 기준은 [사용자 가이드](guide.md)와 `fin capabilities`이다. 모든 CLI 기능을 업무 화면, 공통 설정, 서버 관리 중 하나에 대응시킨다. CLI 명령의 인자나 파일 경로를 그대로 웹 API로 노출하지 않는다.

### 뱅킹

| 화면 또는 동작 | 연결할 CLI 기능 | 구현 시 보존할 동작 |
| --- | --- | --- |
| 은행 로그인 | 앱 인증, 공동인증서 로그인, 하나인증서 서명 로그인 | 서버에 준비된 프로필·인증서를 사용하고 필요한 인증 단계 구별 |
| 계좌 목록·잔액 | `hana accounts`, `hana onesign accounts` | 계좌 정보·조회 시각·금액 표시와 숨김 |
| 거래 내역·상세 | `hana history clock/account/page/detail` | 기간·입출금·검색·정렬·페이지 조건; 다음 페이지는 사용자가 요청 |
| 내역 저장 | `hana history export` | 조회한 페이지를 JSON·CSV로 저장 |
| 이체 내역·상세 | `hana inquiry history/detail` | 기존 이체와 서비스가 제공하는 결과 확인 |
| 원화 이체 | `hana transfer prepare/show/execute/reconcile` | 수취인·금액·수수료 확인, 명시적 실행, 중복 실행 방지, 결과 재조회 |
| 보안매체·한도 | `hana security`의 조회 기능 | 이체한도·예외·보안매체·OTP·사고·모바일 OTP 상태 조회 |
| 로그인 연장 | `hana session extend` | 요청 결과와 현재 세션 상태를 구별 |

OTP 발급·한도 변경은 실행 범위에 포함하지 않는다. 이체에서 지원하지 않는 추가 인증이 요구되면 현재 CLI의 중단 동작과 이유를 그대로 전달한다.

현재 하나인증서 이체는 로그인 세션 하나에 이체 하나를 준비한다. 다음 이체는 새 세션 로그인부터 진행하며, 서버가 이 세션 수명 규칙을 보존한다. 결과 재조회에서 계좌·금액이 같은 내역을 찾았더라도 준비한 거래와의 연결을 확인하지 못하면 해당 이체의 성공으로 확정하지 않는다.

## 구성

초기 구현은 단일 사용자·단일 서버로 구성하되 사용자 한 명의 여러 업무 프로필과 기관 연결을 지원한다. Python API와 정적 웹앱을 같은 서버에서 제공하고, 브라우저에는 CLI나 Python 런타임을 포함하지 않는다.

| 구성 요소 | 구현 방향 |
| --- | --- |
| API | `src/finance_cli/server/`에 FastAPI 기반 API 추가; 서버 의존성은 `web` 선택 설치 항목으로 분리 |
| 시작 명령 | `fin server start` 추가; 기본 바인딩은 `127.0.0.1` |
| 프런트엔드 | `web/app/`에 시안의 HTML·CSS·JavaScript를 옮겨 제품 코드로 관리; 초기에는 별도 UI 프레임워크 없이 시작 |
| 업무 연결 | 허용된 작업별 어댑터로 기존 Python 업무 함수를 재사용; HTTP 경로에서 CLI `main()`을 호출하지 않음 |
| 작업 실행 | 별도 작업 프로세스에서 수행; HTTP 요청은 작업 접수와 조회만 담당 |
| 공통 설정 | 버전 있는 `profiles.json`에 업무 프로필·기관 연결·인증 수단 참조 보관; CLI·서버 공통 접근 계층 사용 |
| 상태 저장 | 사용자 데이터 디렉터리의 SQLite에 접속·작업·실행 예약·산출물 메타데이터 저장 |
| 파일 저장 | 작업별 전용 디렉터리; 기존 개인 파일 권한·새 파일 저장 규칙 유지 |
| 배포 | 패키지에 제품용 정적 자산 포함; 저장소 경로 없이 설치본만으로 실행 |

`web/preview/`는 가상 데이터 시안으로 보존하며 실제 서비스에 연결하지 않는다. 제품용 `web/app/`에서는 예시 데이터와 시연용 완료 처리를 제거한다. 정적 자산은 빌드 또는 패키징 단계에서 패키지 리소스로 넣고, 서버는 설치된 리소스만 제공한다.

### 업무 함수와 CLI 호환

현재 명령 처리에는 인자 해석·숨김 입력·파일 저장·업무 실행이 함께 있는 부분이 있다. 필요한 경로부터 인자 해석과 터미널 입출력을 분리하고, CLI와 서버가 같은 업무 함수를 호출하도록 정리한다. CLI의 옵션·JSON 결과·종료코드 계약은 유지한다.

기존 `--profile`의 인증서 선택 의미는 호환 매핑으로 유지한다. 새 연결 모델은 `--connection`과 용도별 인증 설정으로 확장하며 여러 후보 중 첫 연결을 임의 선택하지 않는다. 설정 이행·미설정 대상·구버전 병용 제한은 프로필 설계를 따른다.

함수 분리 전에는 해당 업무만 고정된 명령 목록과 인자 배열로 별도 프로세스에서 실행할 수 있다. 셸 문자열, 사용자 지정 실행 파일, 임의 옵션은 허용하지 않는다. 비밀은 인자·환경변수에 넣지 않고 전용 입력 채널로 전달한다. 웹 요청 프로세스에서 환경변수를 바꾸거나 표준출력을 전역 가로채지 않는다.

기관별 Node·JDK 등 기존 실행 요구사항은 서버에서 충족한다. 웹앱을 위해 기관 업무에 브라우저 자동화 의존성을 추가하지 않는다.

## API 계약

API 경로는 `/api/v1`로 시작한다. 웹앱과 같은 출처에서 제공하며 임의 출처의 CORS 요청은 허용하지 않는다. 아래 경로는 구현할 인터페이스이며 현재 존재하는 API가 아니다.

| 경로 | 역할 |
| --- | --- |
| `GET /capabilities`, `GET /profiles/{profile_id}/capabilities` | 전체 구현 범위와 프로필·기관 연결별 사용 가능 상태·사유 |
| `POST /auth/enroll`, `POST /auth/logout` | 새 브라우저 접속 등록과 현재 접속 종료 |
| `GET /auth/devices`, `DELETE /auth/devices/{id}` | 등록한 브라우저 접속 확인·철회 |
| `GET/POST /profiles`, `PATCH /profiles/{profile_id}` | 업무 프로필 조회·생성·수정·사용 중지; 기관 접속은 실행하지 않음 |
| `GET/POST /profiles/{profile_id}/connections`, `PATCH /profiles/{profile_id}/connections/{connection_id}` | 기관·채널·업무 대상의 연결 설정; 버전·소속 검사 |
| `GET /credentials` | 자격 증명 표시 정보; 비밀과 파일 경로 제외 |
| `GET /profiles/{profile_id}/connections/{connection_id}/auth-options` | 용도별 지원 인증 방법과 요구 조건 |
| `PUT /profiles/{profile_id}/connections/{connection_id}/auth-bindings/{purpose}` | 로그인·이체 서명·계산서 발급 등 용도별 인증 수단 연결 |
| `GET /profiles/{profile_id}/connections/{connection_id}/session` | 해당 연결의 로그인 주체·대상 확인 상태와 시각 |
| `POST /jobs` | 프로필·기관 연결·업무 이름과 정형화한 입력으로 작업 접수 |
| `GET /jobs`, `GET /jobs/{id}` | 전체 작업 목록·진행·결과·후속 입력 요구 조회 |
| `POST /jobs/{id}/inputs` | 작업이 요청한 입력을 제출; 예상 단계와 입력 유형 검증 |
| `POST /jobs/{id}/confirm` | 준비된 이체·계산서 내용을 확인하고 실행 예약 |
| `POST /jobs/{id}/cancel` | 아직 업무 요청을 시작하지 않은 작업 취소 |
| `GET /artifacts/{id}` | 해당 사용자에게 속한 내역·보고서 다운로드 |

`POST /jobs`의 작업 이름은 `hana.accounts.list`, `hana.transfer.prepare`, `hometax.tax.dues`, `hometax.invoice.prepare`, `giro.bills.parse`처럼 서버에 등록된 값만 허용한다. 명령행·서비스 URL·파일 경로를 요청 본문으로 받지 않는다. 자료 업로드가 필요한 작업은 제한된 크기·형식으로 받은 파일을 서버가 발급한 ID로 참조한다.

기관 업무 요청에는 `profile_id`와 `connection_id`가 필요하다. 서버는 사용자 권한과 두 ID·계좌·초안의 소속을 확인하고, 서버에 저장된 설정으로 실제 고객·사업장을 결정한다. 프로필 선택을 서버 전역에 저장하는 API는 두지 않는다. 프로필·연결 설정 수정은 기대 버전을 받아 동시 변경 충돌을 거절한다.

작업 응답은 다음을 구분한다.

- 실행 상태: `queued`, `running`, `awaiting_input`, `finished`, `cancelled`.
- 업무 결과: `not_started`, `success`, `partial_success`, `rejected`, `unknown`.
- 후속 처리: 문서 저장 상태, 입력 오류, 접속 만료, 처리 오류를 별도 필드로 제공.
- 결과의 출처·조회 시각·프로필·기관 연결·확인된 고객/사업장·설정/인증 수단 버전·산출물 ID를 함께 제공.

프로세스 종료코드나 파일 저장 성공 여부만으로 업무의 성공·실패를 결정하지 않는다. 이미 확인된 성공·부분 성공을 후속 오류로 덮어쓰지 않는다. 알 수 없는 결과는 `unknown`으로 보존한다.

페이지와 커서는 서버가 보관하고 클라이언트에는 불투명한 참조를 제공한다. 모든 작업·파일·후속 입력 요청에 사용자와 접속 권한을 다시 검사한다.

## 실행과 복구

1. 입력·지원 상태·권한·소속을 검사하고 작업 ID와 프로필·기관 연결·실행 설정·인증 수단 버전을 고정한다. 비밀 입력은 작업 JSON이나 로그에 넣지 않는다.
2. 기관별 직렬 실행을 기본으로 하며 실제 공유 세션 자원에 맞춰 공통 잠금을 적용한다. 사업장 선택·대상 확인·업무 실행을 같은 잠금으로 보호하고 사용자 입력 대기 중에는 해제한다. CLI·웹·에이전트가 같은 규칙을 사용하며 재개 시 대상을 다시 확인한다.
3. 이체와 계산서는 준비 결과를 저장한 뒤 사용자 확인을 기다린다. 확인 대상에는 프로필·기관 연결·명의·계좌 또는 사업장·수취인·금액·수수료·초안 ID가 포함된다.
4. 화면의 프로필을 바꿔도 준비한 작업은 기존 대상을 유지한다. 입력·연결 설정·인증 수단 버전·사업장·초안이 달라지면 새 준비·확인이 필요하다. 클라이언트 입력을 실행 직전에 그대로 신뢰하지 않는다.
5. 실행 예약과 시도 여부를 영속화한 뒤 한 번만 전송한다. 중복 확인이나 같은 멱등 키의 동일 요청은 기존 작업을 반환하고 재실행하지 않는다. 사용자·프로필·기관 연결·작업 종류·내용이 다른 키 재사용은 충돌로 거절한다.
6. 전송 이후 응답 유실·프로세스 종료·서버 재시작은 자동 재전송 사유가 아니다. 확인 가능한 결과가 없으면 미확인으로 남긴다.
7. 이체는 지원하는 결과 조회, 계산서는 목록·상세 조회로 확인한다. 기존 성공 기록이 있으면 보존한다. 문서 저장 재처리는 업무 요청 재실행과 별개로 수행한다.
8. 재접속한 브라우저는 저장된 작업 ID로 상태를 다시 조회한다. 초기 버전은 폴링으로 구현하고 연결 해제가 업무 취소를 뜻하지 않도록 한다.

CLI·에이전트에서 실행한 작업도 공통 기록에 연결한다. 이 기능은 지원하는 `fin` 진입 경로에 적용하며, 과거 파일을 읽어 실행을 재현하거나 다시 보내지 않는다.

## 접속과 비밀 관리

초기 운영은 사설 네트워크 또는 VPN 안에서 접속하는 구성을 기본으로 한다. 서버를 공용 인터넷에 노출하는 기능은 기본 설정에 포함하지 않는다. 원격 브라우저 접속에는 HTTPS를 사용하고, 인증서 금고가 있는 호스트와 프런트엔드를 별도 공개 서비스로 나누지 않는다.

웹앱 접속은 은행·홈택스 로그인과 구별한다. 최초 브라우저 등록은 서버의 로컬 관리 명령이 생성한 만료되는 일회성 코드로 진행한다. 코드는 URL·로그에 넣지 않고 한 번 사용하면 폐기한다. 이후 기기별 접속 토큰을 사용하며 서버에는 토큰 해시만 저장한다. 별도 사용자 가입 기능은 만들지 않는다.

접속 쿠키에는 `HttpOnly`, `Secure`, `SameSite=Strict`를 적용한다. 상태 변경 요청은 CSRF 토큰과 출처 검사를 함께 사용한다. 접속 만료·철회·등록 시도 제한을 구현하고, `localStorage`에 접속 토큰이나 기관 비밀을 저장하지 않는다. 로컬 개발용 HTTP 설정은 운영 설정과 명시적으로 구분한다.

자격 증명은 금고 참조로 공유하고 기관 연결별 로그인·서명 용도와 실제 세션·쿠키·추가 인증 상태를 구별한다. 같은 인증서를 쓴다는 이유로 접속 대상이나 권한을 같다고 판단하지 않는다. 웹에서 필요한 PIN·비밀번호는 해당 작업의 현재 단계에만 전달하며 저장·일반 로그·오류 응답에서 제외한다. 자동화에 필요한 비밀은 서버의 기존 보관·접근 방식으로 해결하며 프런트엔드에 전달하지 않는다.

산출물 다운로드는 등록된 ID에만 허용한다. HTML 보고서는 앱과 같은 권한으로 실행하지 않는다. 미리보기는 스크립트와 동일 출처 권한을 허용하지 않는 sandbox로 격리하고, 다운로드는 첨부 파일로 제공한다. 원시 응답 파일·세션 파일·금고 디렉터리는 정적 파일 경로에 포함하지 않는다.

## 지원 상태와 화면 연결

서버가 CLI 지원 정보, 웹 작업 등록 정보, 선택한 프로필·기관 연결·채널·인증 수단의 조건을 합쳐 기능 상태를 반환한다. 프런트엔드는 이 응답을 메뉴·버튼·전체 기능 목록에 동일하게 적용한다.

| 상태 | 화면 | 실행 처리 |
| --- | --- | --- |
| `available` | 사용 가능 | 권한·입력 검사 후 실행 |
| `setup_required` | 설정 필요와 사유 | 필요한 설정이 완료되기 전 실행 불가 |
| `planned` | 준비 중·비활성 | API에서도 `capability_unavailable`로 거절 |
| `local_only` | 서버에서 관리 | 원격 실행 경로 없음 |

각 기능에는 `requires_confirmation`, `requires_input`, `service`, `operation`, 해당 기관 연결을 제공한다. 구현·설정 상태와 별도로 `readiness`에 로그인 필요·추가 입력 필요·대상 미확인·준비 완료를 표시한다. `available`이 현재 로그인이나 업무 대상 확인을 보장하지 않는다. 설치된 런타임이나 선택한 프로필이 달라져도 화면에서 사용 가능하다고 추정하지 않는다. 새 CLI 기능을 추가하면 대응 화면 또는 서버 관리 분류도 함께 추가한다.

## 구현 순서와 완료 기준

각 단계는 앞 단계의 완료 기준을 충족한 뒤 진행한다. 실제 업무 실행 없이 가상 서비스 응답과 로컬 테스트 서버로 검증한다.

| 단계 | 구현할 내용 | 완료 기준 |
| --- | --- | --- |
| 1. 기반 | `web` 선택 의존성, `fin server`, 정적 자산, 버전 있는 업무 프로필·기관 연결·인증 수단 모델, 기존 설정 이행 | 설치본 실행; 기존 CLI 인증서 선택 계약 유지; 프로필 이름으로 명의를 추정하지 않음 |
| 2. 접속·실행 관리 | 브라우저 등록·철회, CSRF, 대상이 고정된 작업 저장, 공통 잠금, 실제 세션과 대상 확인 | 다른 프로필·탭·에이전트의 대상 혼선 없음; 공유 세션의 사업장 전환 직렬화; 재시작·미구현 기능 차단 |
| 3. 조회 기능 | 상단 프로필, 여러 은행 계좌·필터, 뱅킹 조회, 홈택스 대상·세액·신고, 지로 자료 해석 | 연결별 데이터·시각·오류 구별; 이전 프로필 응답 섞임 없음; 미조회 잔액을 0원으로 합산하지 않음 |
| 4. 저장·공통 화면 | 내역·보고서 저장, 통합 작업 기록, 프로필·기관 연결·용도별 인증 설정 | 파일 소속 검사; 문서 불완전 상태 보존; 같은 인증서 공유와 세션 분리; CLI·웹 작업의 대상 표시 |
| 5. 이체·계산서 | 준비·확인·실행·결과 확인, 수정 계산서, 추가 입력 | 중복·응답 유실·재시작 시 재전송 없음; 실행 설정 변경 시 재확인; 성공·부분 성공·미확인 유지 |
| 6. 제품 마무리 | 모바일·PC 반응형, 접근성, 설치·설정 이행 안내, 재접속·복구 | 현재 명의가 항상 보임; 키보드·모바일 사용 가능; 시안과 프로필 설계의 흐름 유지 |

실제 API 연결 시 화면별 로딩·빈 결과·설정 필요·입력 필요·서비스 거절·결과 미확인 상태를 구현한다. 조회 시각과 작업 출처를 표시하고, 기간이나 사업장을 바꾸면 이전 결과가 새 조건의 결과처럼 보이지 않게 한다.
