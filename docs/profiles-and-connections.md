# 업무 프로필·기관 로그인·대상 설계

여러 은행과 개인·개인사업자·법인의 업무를 같은 CLI와 웹앱에서 이용하기 위한 데이터 모델·세션·잠금·CLI 호환 기준이다. 작업 실행·어댑터·접속 계약과 전체 구현 순서는 [웹앱 구현 계획](web-app-plan.md)을 따른다.

현재 CLI의 `--profile`은 기관별 공동인증서 하나를 선택하는 설정이다. 이 문서의 모델·명령·API는 구현 전이며, 새 은행이나 기업뱅킹 지원이 추가되었다는 뜻은 아니다. 현재 어댑터(하나은행 개인, 홈택스, 지로 자료 해석)에 필요한 최소 구조를 먼저 구현한다. 서비스 채널별 규칙이나 한 용도에 여러 수단을 두는 일반화는 그것을 필요로 하는 어댑터를 추가할 때 확장한다.

## 용어

| 용어 | 가리키는 것 | 이 설계에서의 위치 |
| --- | --- | --- |
| 업무 프로필 | 사용자가 묶어 보는 업무 대상의 이름표 | 이 문서와 화면의 "프로필" |
| 인증서 프로필 | 현재 CLI `--profile`과 `profiles.json` | 기관별 인증서 별칭 선택; 호환 매핑으로 유지 |
| 하나은행 앱 프로필 파일 | `hana auth --profile-file`의 앱 헤더·secure_token | 기관 로그인의 기기·앱 등록 정보 |
| 하나인증서 기기 설정 | `hana onesign setup configure`의 기기 속성·공통 헤더 | 기관 로그인의 기기·앱 등록 정보 |

문서와 화면에서 "프로필"은 업무 프로필만 가리킨다. 나머지는 위 이름으로 구별한다.

## 구성과 관계

```
자격 증명 ─(참조)─▶ 기관 로그인 = 기관 × 서비스 채널 × 로그인 주체
                      ├─ 기기·앱 등록 정보 (비밀은 금고·비밀 저장소 참조)
                      ├─ 용도별 서명 수단 기본값
                      ├─ 세션 N개 + 현재 세션 포인터
                      └─ 대상 N개: 기관 응답으로 확인한 개인·사업장·계좌 명의
                            └─ 대상별 서명 수단 지정 (필요한 경우)
업무 프로필 ─(묶음)─▶ 대상 N개
작업 ─(고정)─▶ 로그인·대상·세션 ID·설정 revision·서명 수단
```

| 구성 | 의미 | 주요 정보 |
| --- | --- | --- |
| 자격 증명 | 공동인증서·하나인증서 저장소 등의 보관 참조 | `credential_ref`, 유형, 지문 또는 버전, 표시 정보 |
| 기관 로그인 | 한 기관 서비스에 로그인하는 주체 | `login_id`, 기관, 서비스 채널, 로그인 자격 증명, 서명 수단 기본값, 기기·앱 등록 참조, `revision` |
| 기기·앱 등록 정보 | 자격 증명도 세션도 아닌 기관별 등록 자료 | 하나은행 앱 프로필 파일·로그인 입력, 하나인증서 기기 식별자·설정 |
| 세션 | 기관 접속 한 건 | `session_id`, `login_id`, 생성·확인 시각, 상태(`usable`·`consumed`·`expired`·`stale`), 비공개 저장 위치 참조 |
| 대상 | 로그인으로 이용하는 업무 대상 | `target_id`, `login_id`, 종류, 기관이 돌려준 식별 정보, 확인 시각, 대상별 서명 수단 |
| 업무 프로필 | 대상의 표시 그룹 | `profile_id`, 이름, 유형 표시(`personal`·`sole_proprietor`·`corporation` 또는 미설정), 대상 목록 |
| 작업 | 한 번의 조회·준비·실행 | `job_id`, 요청 출처, 아래 "작업 대상 고정"의 참조 |

- 같은 자격 증명을 여러 로그인이 참조할 수 있으며 인증서·개인키를 복사하지 않는다. 공동인증서와 하나인증서는 기존 보관 방식을 유지하고 한 금고 형식으로 변환하지 않는다. 자격 증명이 같다고 로그인·세션·대상이 같다고 보지 않는다.
- 같은 기관이라도 개인·기업 채널이나 로그인 주체가 다르면 별도 로그인이다.
- 홈택스처럼 로그인 하나로 개인과 여러 사업장을 전환하는 서비스는 로그인 하나 아래에 대상 여러 개를 둔다. 세션 공유는 이 구조로 표현하며 별도의 공유 자원 ID를 두지 않는다.
- 한 대상을 여러 업무 프로필에 넣을 수 있다. 프로필은 표시·필터 단위이며 권한이나 대상 확인의 근거가 아니다.
- 기기·앱 등록 정보 중 앱 키·인증 토큰 같은 비밀은 일반 설정으로 옮기지 않고 기존 비밀 저장소의 참조로 둔다.
- 초기 구현은 단일 사용자다. 요청 출처(웹 접속 기기·CLI·에이전트)는 기록하지만 다중 사용자 권한 모델은 두지 않는다.

다음은 구조를 설명하는 가상 예시이며 특정 은행·채널의 지원을 뜻하지 않는다.

| 기관 로그인 | 대상 | 업무 프로필 |
| --- | --- | --- |
| 은행 A 개인 · 은행 전용 인증 수단 | 본인 명의 계좌 | 내 개인 |
| 홈택스 · 공동인증서 A | 개인 | 내 개인 |
| 홈택스 · 공동인증서 A | A스튜디오 사업장 (계산서 발급: 인증서 B) | A스튜디오 |
| 은행 B 기업 · 법인용 수단 | B회사 계좌 | B회사 |

## 대상 확인

- 대상은 사용자가 고객번호·사업자번호를 입력해 만들지 않는다. 하나은행 계좌는 성공한 계좌 조회 결과로 자동 연결하고, 홈택스 개인·사업장은 확인 결과에서 사용자가 선택한다. 서버는 저장된 작업 결과에서 식별 정보를 가져오며, 브라우저가 보낸 식별 정보를 쓰지 않는다.
- 등록할 때 기관 응답의 식별 정보와 확인 시각을 기록한다. 업무 실행 시 어댑터가 현재 세션에서 같은 대상인지 다시 확인하고, 일치하지 않거나 확인이 부족하면 실행하지 않고 미확인으로 중단한다.
- 하나은행의 새 계좌는 현재 로그인 설정의 성공한 조회 결과에서 자동 추가한다. 기존 계좌의 이름·사용 중지·프로필 묶음을 보존하고 목록 누락만으로 삭제하지 않는다. 서버 시작 시에도 현재 설정 revision에서 성공한 마지막 조회 기록을 사용하며, 추가 은행 요청이나 과거 작업 변경은 하지 않는다. 다른 기관의 대상은 명시적으로 선택한다.
- 프로필 이름·유형, 인증서 이름·발급자·명의, 인증서 프로필 이름으로 개인·사업자·법인, 사업자번호, 이용 권한을 추정하지 않는다. 프로필 유형은 사용자가 지정하는 표시 정보이며 미설정일 수 있다.

## 서명 수단

- 로그인에 용도별 서명 수단 기본값(`login`, `transfer_sign`, `invoice_sign`)을 둔다. 사업장마다 계산서 발급용 인증서가 다른 경우처럼 대상별로 다른 수단이 필요하면 대상에 지정하며, 대상 지정이 로그인 기본값보다 우선한다. 별도의 인증 연결 엔터티는 두지 않는다.
- 하나은행 하나인증서 이체는 별도 설정이 없으면 로그인 인증서를 사용한다. 이는 기본 수단 선택이며, 실패 후 다른 인증서로 바꾸는 재시도가 아니다. 기존 명시적 지정은 보존한다. 계좌 자동 연결이나 업무 프로필 생성이 이체 승인·권한 확인을 대신하지 않는다.
- 실제 사용 가능한 용도와 방법은 기관 어댑터가 정한다. 어댑터에 없는 방법은 실행 가능하다고 표시하지 않는다.
- 만료·실패·권한 부족을 이유로 다른 인증서나 로그인 방법으로 자동 전환하지 않는다. 로그인용 인증서를 계산서 발급용으로 암묵적으로 대신 쓰지 않는다.
- PIN·계좌 비밀번호·일회성 값은 작업 입력이며 설정에 저장하지 않는다.

## 세션

세션의 생성·선택·소모·교체 규칙은 어댑터 계약으로 기관마다 정의한다.

| 기관 | 생성 | 선택·교체 | 소모 |
| --- | --- | --- | --- |
| 하나은행 | 로그인 작업이 이름 있는 세션 디렉터리를 만듦 | 작업이 세션을 명시 | 세션 연장은 요청 결과와 현재 상태를 구별 |
| 하나인증서 이체 | 로그인 작업(`new-session`) | 이체마다 새 세션 | 이체 준비가 세션을 소모; 다음 이체는 새 로그인부터 |
| 홈택스 | 로그인 작업 | 명령마다 세션 파일을 읽고 갱신본을 새 파일에 저장; 로그인별 현재 세션 포인터를 옮김 | 사업장 선택이 세션의 현재 대상을 바꿈 |

- 작업은 실행에 쓸 **구체적인 세션 ID**를 고정한다. 이후 현재 세션 포인터가 바뀌어도 그 작업은 다른 세션으로 넘어가지 않는다. 고정한 세션을 쓸 수 없으면 중단하고 사유를 기록한다.
- 홈택스 세션 저장이 실패하면(`session_file_saved: false`) 포인터를 새 파일로 옮기지 않는다. 기존 포인터도 최신 상태라고 신뢰하지 않도록 `stale`로 표시하고, 다음 작업은 세션 확인 또는 재로그인부터 진행한다. 이미 관측한 업무 판정은 그대로 보존한다.
- 세션 파일은 비공개 세션 저장소에만 두며 산출물이나 API 응답으로 제공하지 않는다(웹앱 계획의 "어댑터 출력 분리").
- 로그인 상태는 마지막 확인 시각과 함께 표시한다. 저장된 성공 기록만으로 현재 유효성을 보장하지 않는다.
- 세션을 복사해 독립성을 가장하지 않는다. 기관이 동시 로그인을 제한하면 그 제약을 상태로 표시한다.

## 잠금과 동시 실행

잠금 범위는 실제로 공유되는 자원을 기준으로 한다. 초기에는 기존 잠금을 유지하고 기관별 직렬 실행을 더한다.

| 자원 | 잠금 | 비고 |
| --- | --- | --- |
| 하나인증서 저장소 | 기존 저장소 전체 잠금 유지 | 서로 다른 로그인이 같은 저장소를 참조할 수 있어 로그인 단위 잠금으로는 부족 |
| 하나은행 세션 | 기존 세션 잠금 유지 | |
| 홈택스 | 새로 추가; 초기에는 기관 단위 직렬 | 로그인 단위로 좁히는 것은 세션 독립성을 확인한 뒤 |
| 설정·작업 저장소 | SQLite 트랜잭션 | |

- 여러 잠금이 필요한 작업은 고정된 순서로 얻는다.
- 대상 선택·대상 확인·업무 실행 전체를 같은 잠금 안에서 실행한다. 사용자 입력을 기다리는 동안에는 잠금을 보유하지 않고, 재개할 때 다시 얻어 대상을 다시 확인한다.
- 기존 잠금은 기다리지 않고 즉시 실패한다. CLI는 이 동작과 기존 오류·종료코드를 유지하고, 웹 작업은 서버 대기열에서 순서를 기다린다. 대기열의 작업은 잠금을 얻은 뒤에 실행 단계에 들어간다.
- 인증서가 같다는 이유만으로 모든 기관을 한 잠금에 묶거나, 프로필·대상이 다르다는 이유만으로 같은 세션의 작업을 병렬 실행하지 않는다.
- 구버전 CLI는 새로 추가하는 잠금에 참여하지 않는다. 이는 파일 호환과 별개의 동시 실행 문제다. 웹 서버와 같은 데이터 디렉터리를 쓰는 CLI·에이전트는 같은 버전으로 갱신해야 하며, 이를 설치·이행 안내에 명시한다.

## 작업 대상 고정

서버에는 전역 현재 프로필을 두지 않는다. 기관 업무 요청은 `login_id`와 필요한 `target_id`를 명시한다. `profile_id`는 표시·필터용으로 기록하며 실행 대상을 결정하지 않는다. 서버는 로그인·대상·계좌·초안의 소속을 확인한 뒤 저장된 설정으로 실제 대상을 정한다.

작업을 접수할 때 다음을 고정한다.

- 요청 출처, 업무 프로필 ID, 로그인 ID와 설정 revision.
- 대상 ID와 기관이 확인한 식별 정보, 계좌 또는 초안 ID.
- 세션 ID.
- 용도별 서명 수단의 자격 증명 ID와 지문 또는 버전.

비밀값은 스냅샷에 넣지 않는다. 처음 로그인하거나 대상을 확인하는 작업은 확인 전의 예상 대상과 기관이 확인한 대상을 별도 필드로 두며, 확인 전부터 검증되었다고 표시하지 않는다.

멱등 키와 확인 토큰은 요청 출처·로그인·대상·작업 종류·입력 내용에 묶는다. 같은 키를 다른 대상이나 내용으로 재사용하면 충돌로 거절한다. 전송 이후에는 결과가 미확인이어도 자동 재전송하지 않는다.

저장된 작업·문서의 과거 대상은 이름 변경·설정 교체 이후에도 식별할 수 있어야 한다. 다운로드와 결과 재조회에도 작업의 소속을 검사한다.

## 설정 변경과 사용 중지

- 실행에 영향을 주는 로그인 설정(로그인 자격 증명, 서명 수단, 기기·앱 등록, 채널)과 대상별 서명 수단은 로그인의 `revision` 하나로 관리한다. 변경되면 영향받는 세션은 재확인이 필요하고 준비된 초안의 확인은 무효가 된다. 이미 전송된 작업은 기존 대상·revision·결과를 유지한다.
- 이름, 프로필 유형 표시, 프로필의 대상 묶음 변경은 실행 설정 변경이 아니다.
- 설정 수정은 기대 revision을 받아 동시 수정 충돌을 거절한다.
- 로그인·대상·프로필을 사용 중지하면 새 업무 접수와 미전송 작업의 실행·재개를 막고 기록은 남긴다. 이미 전송된 작업의 결과 확인은 허용한다. 참조 중인 인증서를 자동 삭제하거나 다른 로그인의 세션을 종료하지 않는다.

## 화면 구성

- 상단 공통 바에 현재 업무 프로필의 이름·유형을 항상 표시한다. 모바일에서도 숨기지 않는다. "전체"를 선택하면 모든 대상을 모아 본다.
- 좌상단 뱅킹·지로·세금 전환과 영역별 메뉴는 유지한다. 화면 기억은 프로필별로 분리한다.
- 뱅킹의 내 계좌는 현재 프로필의 계좌 대상을 은행·로그인별로 모으고 필터를 제공한다. 계좌와 이체 입력에는 은행·로그인·명의를 표시한다.
- 로그인별로 로그인됨·로그인 필요·추가 입력 필요·대상 확인 필요 상태와 마지막 확인 시각을 표시한다. 한 은행의 조회 실패가 다른 은행의 결과를 없애지 않으며, 미조회 잔액을 0원으로 합산하지 않는다.
- 세금 화면은 현재 프로필의 홈택스 대상을 사용한다. 대상이 여러 개면 현재 대상을 화면에 드러내어 선택하게 하며, 숨은 선택으로 표시와 실제 대상이 어긋나지 않게 한다.
- 연결·인증서 화면에서 로그인별 자격 증명·기기 등록·세션과 조회된 계좌를 확인한다. 하나인증서의 기본 이체 인증서는 별도 설정으로 표시하지 않으며, 업무 프로필 묶음은 선택 사항이다. 홈택스 발급용 등 별도 서명 수단은 해당 용도로 관리한다. 웹앱 접속 기기는 기관 세션과 별도로 표시한다.
- 작업 기록은 현재 프로필을 기본 필터로 하고 전체 보기로 확장한다. 각 행에 대상·로그인·요청 출처를 표시한다.
- 미구현 기관·기능은 준비 중으로 표시하고 비활성화한다. 설정 부족·로그인 만료·대상 미확인은 미구현과 구별한다.

프로필 전환은 해당 탭의 표시 대상만 바꾼다. 다른 탭·기기·에이전트의 대상, 진행 중인 작업, 기관의 실제 로그인 상태를 바꾸지 않는다. 연결된 모든 기관에 자동 로그인하지 않고 업무에 필요할 때 접속을 확인한다.

프런트엔드의 조회·캐시 키는 로그인·대상·조회 조건을 포함한다. 이전 프로필에서 늦게 도착한 응답을 새 프로필의 결과로 표시하지 않는다. 진행 중인 작업을 볼 때는 현재 화면 프로필과 다르더라도 그 작업에 고정된 대상을 분명히 표시한다.

현재 [정적 시안](../web/preview/README.md)은 영역 전환과 홈택스 내부의 개인/사업장 전환까지 표현한다. 상단 업무 프로필, 여러 은행의 통합 계좌, 로그인·대상·서명 수단 설정은 이 설계에 맞춰 추가해야 한다.

## API

아래는 `/api/v1` 아래의 설정·모델 경로다. 작업·접속·산출물 경로는 [웹앱 구현 계획](web-app-plan.md#api-계약)에 있다.

| 경로 | 역할 |
| --- | --- |
| `GET /logins`, `POST /logins`, `PATCH /logins/{login_id}` | 기관 로그인 조회·추가·수정·사용 중지; 기관 접속은 실행하지 않음; 기대 revision 검사 |
| `GET /logins/{login_id}/auth-options` | 어댑터가 지원하는 용도별 로그인·서명 방법과 요구 조건 |
| `GET /logins/{login_id}/sessions` | 세션 목록·상태·현재 포인터·마지막 확인 시각; 쿠키·세션 파일 제외 |
| `GET /logins/{login_id}/targets`, `POST /logins/{login_id}/targets` | 등록된 대상과 확인 상태; 확인 작업 결과의 항목 참조로 대상 등록 |
| `PATCH /targets/{target_id}` | 대상별 서명 수단·표시 이름·사용 중지 |
| `GET /profiles`, `POST /profiles`, `PATCH /profiles/{profile_id}` | 업무 프로필과 대상 묶음 |
| `GET /credentials` | 자격 증명 표시 정보; 비밀·파일 경로 제외 |
| `GET /capabilities`, `GET /profiles/{profile_id}/capabilities` | 전역 구현 범위, 프로필 대상별 사용 가능 상태·준비 상태·검증 수준 |

프로필 선택 상태를 서버 전역에 저장하는 API는 두지 않는다. 집계 화면의 조회는 대상별 개별 작업으로 실행하며, 각각의 성공·실패·미확인과 조회 시각을 보존한다.

## 저장소와 기존 CLI 호환

현재 `profiles.json`은 `인증서 프로필 이름 → 기관 → 인증서 별칭과 지문` 구조이고, `--profile`은 인증서만 선택한다. 이 동작을 명의 확인이나 업무 권한 확인으로 소급 해석하지 않는다.

- 새 모델(로그인·대상·업무 프로필·세션 메타데이터·작업)은 사용자 데이터 디렉터리의 SQLite 하나에 저장한다. 표준 라이브러리 `sqlite3`만 사용한다. 설정 revision 검사와 작업 고정을 한 트랜잭션에서 처리한다.
- 기존 `profiles.json`은 형식을 바꾸지 않고 인증서 프로필(호환 매핑)의 원본으로 쓴다. 구버전과 새 CLI가 같은 형식을 읽고 쓰므로 구버전이 새 설정을 오염시키지 않으며, `profile list/set`의 JSON 계약도 그대로 유지된다.
- 이행은 명시적 가져오기 명령으로 한다. `profiles.json`을 읽기 전용으로 읽어 로그인 설정 초안을 만들고, 기존 이름·인증서 지문을 보존한다. 유형·명의·사업장·서비스 채널은 추정하지 않고 미설정으로 둔다. 대상은 확인 작업으로만 등록한다. 기존 파일은 수정하지 않는다.
- SQLite 트랜잭션은 세션 파일·인증서 금고·기관 요청을 포함하지 않는다. 설정 DB 백업, 세션 저장 실패 시의 `stale` 처리, 기관 요청 전후 상태 영속화(웹앱 계획의 "실행과 복구")는 계속 필요하다.
- `--profile`과 `--credential`은 기존 의미를 유지한다. 새 모델을 쓰는 경로는 `--login`과 필요한 경우 `--target`을 명시한다. 후보 중 첫 항목이나 마지막으로 쓴 항목을 임의로 선택하지 않는다. `--profile`과 `--login`을 함께 지정하면 서로 다른 체계이므로 거절한다.
- `--login` 경로에서 `--credential`도 받으면 해당 용도에 허용된 수단인지 검사하고, 충돌하면 임의 우선순위로 실행하지 않고 설정 확인을 요구한다.
- 인증서 지문이 바뀌었을 때 다른 인증서를 자동 선택하지 않는 기존 보호를 유지한다.
- 호환 경로의 작업도 공통 기록에 남기되, 확인되지 않은 대상을 임의 프로필에 귀속하지 않는다. 기록 실패는 CLI의 JSON 결과나 종료코드를 바꾸지 않는다.

## 완료 기준

테스트는 가상 기관 응답과 로컬 전송 계층만 사용한다. 단계별 순서는 [웹앱 구현 계획](web-app-plan.md#구현-순서와-완료-기준)을 따른다.

| 경우 | 확인할 결과 |
| --- | --- |
| 한 홈택스 로그인의 개인·여러 사업장 | 대상별로 등록·선택; 대상 선택·확인·실행이 직렬화되고 각 결과의 대상이 일치 |
| 사업장마다 다른 계산서 발급용 인증서 | 대상별 서명 수단 사용; 누락·만료 시 다른 수단으로 자동 대체하지 않음 |
| 여러 로그인에서 같은 인증서 사용 | 금고 자료는 한 번만 보관; 세션·대상·결과는 섞이지 않음 |
| 같은 하나인증서 저장소를 참조하는 두 로그인 | 저장소 잠금으로 직렬화 |
| 작업 중 홈택스 현재 세션 포인터 변경 | 작업은 고정한 세션 ID만 사용 |
| 홈택스 세션 저장 실패 | 포인터를 옮기지 않고 `stale` 표시; 관측한 업무 판정은 보존 |
| 웹 대기열과 CLI 동시 실행 | 웹은 대기, CLI는 기존 즉시 실패 계약 유지 |
| 개인 탭·법인 탭·자동화 동시 실행 | 전역 현재 프로필 없이 각 요청의 대상 유지 |
| 프로필 전환 뒤 늦게 도착한 응답 | 새 프로필의 화면·잔액에 섞이지 않음 |
| 초안 이후 화면 프로필만 전환 | 기존 작업 대상 유지 |
| 초안 이후 로그인 revision 변경 | 재준비·재확인 요구; 이미 전송된 결과는 보존 |
| 브라우저가 보낸 식별 정보로 대상 등록 시도 | 거절; 확인 작업 결과의 항목 참조만 허용 |
| 서로 다른 대상에 같은 멱등 키 사용 | 충돌로 거절 |
| 일부 은행 조회 실패·미조회 | 로그인별 상태·시각 보존; 미조회 잔액을 0원으로 합산하지 않음 |
| 가져오기와 구버전 CLI | `profiles.json` 무변경; 구버전의 `profile set` 이후에도 새 설정 유지 |

구현은 문서 작성과 별도 단계이며 실제 인증서 발급·로그인·이체·계산서 발급을 실행하지 않는다.
