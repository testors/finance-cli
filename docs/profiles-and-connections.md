# 업무 프로필과 기관 연결 설계

여러 은행과 개인·개인사업자·법인의 업무를 같은 CLI와 웹앱에서 이용하기 위한 설계다. 업무 프로필은 **어떤 명의와 자격으로 업무를 수행하는가**를 나타낸다. 기관별 로그인 수단과 업무용 인증서는 그 프로필 아래의 기관 연결에 지정한다.

이 문서는 [웹앱 구현 계획](web-app-plan.md)의 프로필·접속 모델을 구체화한 구현 기준이다. 현재 CLI의 프로필은 기관별 공동인증서 하나를 선택하는 설정이며, 아래 모델과 추가 명령·API는 구현 전이다. 여러 기관을 담을 수 있는 구조를 마련하는 것이며 새 은행이나 기업뱅킹 지원이 이미 추가되었다는 뜻은 아니다.

## 구분과 관계

| 구성 | 의미 | 주요 정보 |
| --- | --- | --- |
| 사용자 | 웹앱·CLI·에이전트를 사용하는 주체 | `actor_id`, 접근 가능한 프로필; 초기에는 단일 사용자 |
| 업무 프로필 | 개인 또는 특정 사업장·법인이라는 업무 대상 | `profile_id`, 이름, 유형, 대상 참조, 기존 CLI 별칭 |
| 기관 연결 | 해당 프로필로 이용할 특정 기관 서비스 | `connection_id`, `profile_id`, 기관, 개인/기업 등 서비스 채널, 기관의 고객·사업장 대상, 설정 버전 |
| 인증 수단 연결 | 기관 연결의 특정 업무에 사용할 로그인·서명 방법 | `binding_id`, `connection_id`, 용도, 방법, 자격 증명 참조, 버전 |
| 자격 증명 | 인증서·은행 전용 인증 수단·비밀 입력의 보관 참조 | `credential_ref`, 유형, 지문 또는 버전, 표시 정보; 비밀은 기존 금고에 보관 |
| 기관 세션 | 실제 기관 접속과 확인된 대상 | `session_id`, 기관 연결, 로그인 주체, 현재 고객·사업장, 확인 시각, 인증 수단 버전, 공유 세션 자원 ID |
| 작업 | 한 번의 조회·준비·실행과 그 결과 | `job_id`, 요청 주체, 대상 프로필·기관 연결, 입력·확인 내용, 실행 시도와 결과 |

프로필 하나에 여러 기관 연결이 있고, 기관 연결 하나에 로그인·이체 서명·계산서 발급 등 용도별 인증 수단을 지정한다. 동일 기관도 개인뱅킹·기업뱅킹 또는 고객 계약이 다르면 별도 연결로 둔다. `(profile_id, service)`를 한 연결만 허용하는 키로 사용하지 않는다.

같은 자격 증명을 여러 연결에서 참조할 수 있으며 인증서·개인키를 복사하지 않는다. 공동인증서와 하나인증서는 기존 보관 방식을 유지하고 유형이 있는 참조로 연결한다. 한 금고 형식으로 강제 변환하지 않는다. 인증서를 함께 쓴다는 이유로 기관 세션이나 업무 대상까지 같은 것으로 간주하지 않는다.

### 업무 프로필의 단위

사용자에게 보이는 유형은 개인(`personal`), 개인사업자(`sole_proprietor`), 법인(`corporation`)이다. 별개의 개인사업장 두 곳은 각각 별도 프로필이며 같은 법인을 위한 기관 연결은 하나의 프로필에 모은다. 유형만으로 은행 서비스 채널이나 로그인 수단을 결정하지 않는다.

다음은 구조를 설명하는 가상 예시이며 특정 은행·채널의 지원을 의미하지 않는다.

| 프로필 | 기관 연결 | 용도별 인증 수단 |
| --- | --- | --- |
| 내 개인 | 은행 A 개인 서비스 | 로그인: 은행 전용 인증 수단 |
| 내 개인 | 은행 B 개인 서비스 | 로그인: 공동인증서 A |
| A스튜디오 · 개인사업자 | 홈택스 A사업장 | 로그인: 공동인증서 A / 계산서 발급: 발급용 인증서 B |
| A스튜디오 · 개인사업자 | 은행 A 사업자 서비스 | 해당 서비스가 지원하는 로그인·서명 수단 |
| B회사 · 법인 | 은행 B 기업 서비스 | 법인용 로그인·업무 인증 수단 |

프로필 이름은 표시용이며 권한이나 기관의 대상 확인 근거로 사용하지 않는다. 사용자가 설정한 대상과 기관 응답에서 확인한 대상을 구별한다. 인증서 이름·발급자·명의나 기존 CLI 프로필 이름만 보고 개인/사업자/법인, 사업자번호, 이용 권한을 추정하지 않는다.

## 기관 연결과 인증 수단 설정

기관 어댑터는 기관·서비스 채널·프로필 유형·작업별로 지원하는 로그인 방법, 필요한 인증 수단, 추가 입력, 대상 확인 방법을 정의한다. 하나은행의 로그인·세션·이체 규칙을 다른 은행의 공통 규칙으로 확대하지 않는다.

인증 수단 연결의 `purpose`는 최소한 `login`, `transfer_sign`, `invoice_sign`을 구별한다. 실제 사용 가능한 용도와 방법은 기관 어댑터가 결정한다. 비밀번호나 사용자 확인 등 인증서를 쓰지 않는 방법도 표현할 수 있게 하되, 어댑터에 없는 방법은 실행 가능하다고 표시하지 않는다. PIN·일회성 값은 작업의 후속 입력으로 취급하며 프로필에 평문으로 저장하지 않는다.

한 용도에 여러 방법을 등록할 수 있어도 기본값은 하나만 명시적으로 지정한다. 사용자가 대안을 고를 수 있지만, 만료·실패·권한 부족을 이유로 서버가 다른 인증서나 로그인 방법으로 자동 전환하지 않는다. 로그인용 인증서를 계산서 발급용으로 암묵적으로 대신 사용하지 않는다.

연결 설정 저장은 기관 로그인이나 인증서 발급을 실행하지 않는다. 원격으로 기관을 확인할 때는 별도의 명시적 연결 확인 작업을 생성한다. 대상이 미확인이면 로그인·대상 조회 같은 확인 작업만 허용하고, 계좌·사업장 업무는 해당 어댑터가 대상을 확인한 뒤 진행한다. 일치하지 않으면 실행을 중단하고 설정된 대상과 확인된 대상이 다르다는 이유를 표시한다.

인증 수단 교체나 실행에 영향을 주는 연결 설정 변경은 버전을 올린다. 영향받는 세션은 재확인이 필요해지고 기존 초안의 확인은 무효화한다. 이미 전송한 작업은 기존 대상·인증 수단 버전·결과를 유지한다. 표시 이름만 바꾸는 것은 실행 설정 변경으로 취급하지 않는다.

프로필이나 연결을 사용 중지하면 새 업무 접수와 미전송 작업의 실행·재개를 막고 작업·산출물 기록은 남긴다. 이미 전송된 작업의 결과 확인은 허용한다. 참조 중인 인증서를 자동 삭제하거나 다른 프로필의 세션을 임의로 종료하지 않는다.

## 화면 구성

- 상단 공통 바에 `A스튜디오 · 개인사업자`처럼 현재 프로필 이름과 유형을 항상 표시한다. 모바일에서도 현재 업무 대상을 숨기지 않는다.
- 좌상단 뱅킹·지로·세금 전환과 영역별 메뉴는 유지한다. 화면 기억은 프로필별로 분리한다.
- 뱅킹의 내 계좌는 현재 프로필에 연결된 은행들을 모아서 보여 주고 은행·서비스 연결별 필터를 제공한다. 계좌와 이체 입력에는 은행뿐 아니라 기관 연결과 명의를 식별할 수 있게 표시한다.
- 은행별 로그인됨·로그인 필요·추가 입력·대상 확인 필요 상태와 마지막 조회 시각을 표시한다. 한 은행의 조회 실패가 다른 은행의 결과를 없애지 않으며, 미조회 잔액을 0원으로 합산하지 않는다.
- 세금 화면은 현재 프로필의 홈택스 연결 대상을 사용한다. 다른 사업장으로 바꾸려면 그 사업장의 프로필로 전환하거나 새 프로필을 설정한다. 별도의 숨은 사업장 선택으로 전역 프로필 표시와 실제 대상이 어긋나게 하지 않는다.
- 연결·인증서 화면에서 프로필별 기관 연결, 로그인 방법, 용도별 인증 수단, 확인된 고객·사업장, 기관 세션을 관리한다. 웹앱 접속 기기는 이 기관 세션과 별도 항목으로 표시한다.
- 작업 기록은 현재 프로필을 기본 필터로 하고 전체 프로필 보기로 확장한다. 각 행에 프로필·기관 연결·요청 출처를 표시한다.
- 기관이나 기능이 미구현이면 준비 중으로 표시하고 비활성화한다. 설정 부족·로그인 만료·대상 미확인은 미구현과 구별한다.

프로필 전환은 해당 탭의 표시 대상만 바꾼다. 다른 탭·기기·에이전트의 기본 대상, 진행 중인 작업, 기관의 실제 로그인 상태를 변경하지 않는다. 연결된 모든 기관에 자동 로그인하지 않고, 해당 업무에서 필요할 때 접속을 확인한다.

프런트엔드의 조회·캐시 키는 프로필·기관 연결·업무 대상·조회 조건을 포함한다. 이전 프로필에서 늦게 도착한 응답을 새 프로필의 결과로 표시하지 않는다. 진행 중인 작업을 확인할 때는 현재 화면 프로필과 다르더라도 **그 작업에 고정된 대상**을 분명히 표시한다.

현재 [정적 시안](../web/preview/README.md)은 영역 전환과 홈택스 내부의 개인/사업장 전환까지 표현한다. 상단 업무 프로필, 여러 은행의 통합 계좌, 기관 연결·용도별 인증 설정은 이 설계에 맞춰 구현해야 할 추가 항목이다.

## 세션과 동시 실행

논리적인 기관 연결을 분리했다고 실제 기관 세션까지 독립적이라고 가정하지 않는다. 같은 로그인 주체·기기 등록·쿠키 세션이 여러 사업장을 전환하는 서비스는 실제로 공유되는 자원을 기준으로 충돌을 조정한다.

기본 동작은 기관별 직렬 실행이다. 어댑터가 세션 독립성을 보장할 수 있는 경우에만 더 좁은 자원 범위로 나눈다. 두 프로필이 하나의 기관 세션을 사용하는 경우 다음 절차 전체를 같은 잠금 안에서 실행한다.

1. 사용할 인증 수단 버전과 실제 로그인 주체를 확인한다.
2. 기관이 허용하는 방법으로 필요한 고객·사업장 대상을 선택한다.
3. 기관 응답으로 대상 일치를 확인한다. 확인이 부족하면 미확인으로 중단한다.
4. 해당 작업을 실행하고 확인된 대상과 결과를 기록한 뒤 잠금을 해제한다.

사용자 확인이나 추가 입력을 기다리는 동안에는 잠금을 보유하지 않는다. 재개할 때 다시 잠금을 얻고 동일 대상을 확인한다. 그 사이 변경된 세션을 그대로 신뢰하지 않는다. 실제 세션을 복사하여 독립성을 가장하지 않으며, 기관이 동시 로그인을 제한하면 해당 제약을 상태로 표시한다.

동일 데이터 디렉터리를 사용하는 웹·CLI·에이전트는 같은 자원 잠금 규칙을 적용한다. 인증서가 같다는 이유만으로 모든 기관을 한 잠금에 묶거나, 프로필 ID가 다르다는 이유만으로 동일 세션의 작업을 병렬 실행하지 않는다.

## 작업 대상과 확인

서버에는 하나의 전역 현재 프로필을 두지 않는다. 모든 기관 업무 요청은 `profile_id`, `connection_id`를 명시한다. 서버는 두 ID의 관계, 요청 사용자의 권한, 계좌·사업장·초안의 소속을 확인한 뒤 서버에 저장된 설정으로 업무 대상을 결정한다. 브라우저가 보낸 고객번호·사업자번호로 소속 검사를 대신하지 않는다.

작업을 접수할 때 다음 참조와 버전을 고정한다.

- 요청 사용자와 출처, 프로필 ID, 기관 연결 ID·실행 설정 버전.
- 기관이 확인한 고객·사업장 대상, 계좌 또는 초안 ID.
- 용도별 인증 수단 연결 ID·버전, 자격 증명 ID·지문 또는 버전.
- 필요한 기관 세션 또는 세션 자원 참조; 재개 시 대상과 유효성은 다시 확인.

비밀값 자체는 작업 스냅샷에 저장하지 않는다. 입력한 비밀은 해당 작업 ID·현재 단계에만 전달하고 재사용 가능한 공통 입력으로 취급하지 않는다.

처음 로그인하거나 연결 대상을 확인하는 작업은 아직 확인되지 않은 예상 대상을 고정하고, 기관이 확인한 대상은 별도 결과로 기록한다. 확인 전부터 대상이 검증되었다고 표시하지 않는다. 로그인 상태도 마지막 확인 시각과 함께 표시하며 저장된 성공 기록만으로 현재 유효성을 보장하지 않는다.

이체·계산서의 확인 화면은 프로필 이름·유형·기관 연결·명의·수취인·금액·수수료·초안을 함께 보여 준다. 확인 요청은 저장된 초안과 설정 버전을 대상으로 한다. 화면의 프로필을 바꿔도 기존 작업이 새 프로필로 이동하지 않으며, 실행 설정이나 인증 수단 버전이 바뀌면 새 준비·확인이 필요하다.

멱등 키와 확인 토큰도 요청 사용자·프로필·기관 연결·작업 종류·입력 내용에 묶는다. 같은 키를 다른 대상이나 내용으로 재사용하면 기존 작업을 실행하거나 다른 결과를 반환하지 않고 충돌로 거절한다. 전송 이후에는 결과가 미확인이어도 자동 재전송하지 않는다.

저장된 작업·문서의 과거 대상은 프로필 이름 변경·연결 교체 이후에도 식별할 수 있어야 한다. 다운로드와 결과 재조회에도 작업의 소속과 현재 사용자 권한을 검사한다.

## API 변경

아래는 `/api/v1` 아래에 구현할 계약이다. 기존 계획의 기관당 인증서 하나를 설정하는 경로와 기관 이름만으로 세션을 조회하는 경로를 대체한다.

| 경로 | 역할 |
| --- | --- |
| `GET /profiles`, `POST /profiles`, `PATCH /profiles/{profile_id}` | 업무 프로필 조회·생성·수정·사용 중지; 기관 접속은 실행하지 않음 |
| `GET /profiles/{profile_id}/connections`, `POST /profiles/{profile_id}/connections` | 기관 연결 목록·설정 추가 |
| `PATCH /profiles/{profile_id}/connections/{connection_id}` | 대상·채널 등 연결 설정 변경; 버전 검사 |
| `GET /profiles/{profile_id}/connections/{connection_id}/auth-options` | 선택 가능한 용도별 로그인·서명 방법과 요구 조건 |
| `PUT /profiles/{profile_id}/connections/{connection_id}/auth-bindings/{purpose}` | 용도별 인증 수단 연결과 명시적 기본값 지정 |
| `GET /profiles/{profile_id}/connections/{connection_id}/session` | 해당 연결의 로그인·대상 확인 상태; 기관 쿠키는 제외 |
| `GET /credentials` | 허용된 자격 증명의 유형·표시 정보; 비밀·파일 경로는 제외 |
| `GET /capabilities` | 전역 구현 범위와 기관·채널 목록 |
| `GET /profiles/{profile_id}/capabilities` | 선택한 프로필의 연결·설정·인증 상태에 따른 실제 사용 가능 기능 |
| `POST /jobs` | 프로필·기관 연결을 명시한 업무 접수; 확인·입력·취소는 기존 작업 ID 경로 사용 |

프로필·연결 설정 변경은 기대하는 설정 버전을 받아 동시 수정 충돌을 거절한다. 프로필 선택 상태를 서버 전역에 저장하는 API는 제공하지 않는다. 집계 화면의 조회는 프로필의 각 기관 연결에 소속된 개별 작업으로 실행하며 성공·실패·미확인과 조회 시각을 각각 보존한다.

로그인 필요나 대상 미확인은 준비 중인 기능과 다르다. 기능의 구현·설정 상태와 별도로 `readiness`에 `ready`, `login_required`, `input_required`, `target_unverified` 등을 제공한다. `available` 표시만 보고 바로 업무를 실행하지 않고 연결별 준비 상태를 서버에서 다시 확인한다.

## 기존 CLI와 설정 호환

현재 `profiles.json`은 `프로필 이름 → 기관 → 인증서 별칭과 지문` 구조다. `--profile`은 인증서만 선택하며 개인·사업장·세션을 선택하지 않는다. 이 동작을 명의 확인이나 업무 권한 확인으로 소급 해석하지 않는다.

새 구성은 버전 2의 `profiles.json`에 업무 프로필·기관 연결·인증 수단 연결·기존 별칭 매핑을 저장한다. 금고와 세션 파일은 참조만 보관하며, 작업과 실제 세션 메타데이터는 기존 서버 계획의 저장소를 사용한다. 구성의 읽기·쓰기·잠금은 CLI와 서버가 공유하는 공통 계층으로 구현한다.

이행 순서는 다음과 같다.

1. 새 CLI는 기존 형식을 읽을 수 있게 한다. 읽기만으로 설정을 덮어쓰거나 실제 기관에 접속하지 않는다.
2. 명시적 이행 명령에서 기존 이름·인증서 지문을 보존하고, 금고 밖의 인증서를 복사하지 않는 변환안을 만든다. 프로필 유형·명의·사업장·서비스 채널은 자동 추정하지 않고 미설정 상태로 둔다. 미설정 프로필의 유형은 비워 두며 임의로 개인 유형을 배정하지 않는다.
3. 사용자가 필요한 업무 대상과 연결을 지정한 뒤 버전 2를 저장한다. 원래 설정은 같은 비공개 데이터 영역에 백업하고 새 설정은 잠금과 원자적 교체로 저장한다. 일부 저장 실패가 절반만 변환된 설정을 남기지 않게 한다.
4. 기존 `--profile 이름`과 `--credential 별칭` 선택 동작은 유지한다. 기존 프로필 별칭에는 별도의 호환 인증서 매핑을 남겨 동일한 인증서·지문 검사와 결과 계약을 적용한다. 예전 로그인용/발급용 별칭을 임의로 합치지 않는다.
5. 새 연결 모델을 사용하는 CLI 경로에는 `--connection`을 추가하고 명시적으로 지정하도록 한다. 이 옵션이 없는 기존 명령은 호환 인증서 선택 동작을 유지한다. 후보 중 첫 연결이나 화면의 마지막 연결을 임의 선택하지 않으며, `--profile`과 `--connection`의 소속 불일치는 거절한다.
6. 기존의 `profile set --service ... --cert ...`는 호환 인증서 매핑을 변경한다. 새 연결의 로그인·이체·발급용 설정을 함께 바꾸지 않는다. 새 용도별 설정은 명시적인 연결·용도 인자를 받는 명령으로 분리한다.

호환 매핑만 있는 프로필은 기존 CLI의 인증서 선택에는 사용할 수 있지만, 검증되지 않은 명의로 새 웹 업무를 실행할 수는 없다. 새 모델의 명의·소속·세션 검사는 해당 연결을 사용하는 경로에 적용한다. 호환 경로 역시 공통 실행 잠금과 작업 기록을 적용하되 확인되지 않은 대상을 임의 프로필에 귀속하지 않는다.

여러 기존 별칭을 하나의 업무 프로필에 연결하려면 사용자가 그 관계를 지정해야 한다. 별칭별·기관별 호환 인증서 매핑은 계속 구별한다. 기존 `profile list/set`의 JSON 계약은 호환 뷰로 유지하고 내부 버전 2 저장 형식을 그대로 출력하지 않는다. 새 기관 연결과 인증 용도 조회는 별도 명령이나 명시적인 확장 옵션으로 제공한다.

`--connection`으로 새 경로를 선택하면 해당 연결의 용도별 인증 설정을 기준으로 한다. 기존 별칭의 호환 인증서가 이를 암묵적으로 덮어쓰지 않는다. 이 경로에서 `--credential`도 받는 경우에는 해당 용도에 등록되고 허용된 수단인지 검사한다. 두 선택 방식이 충돌하면 임의 우선순위로 실행하지 않고 설정 확인을 요구한다.

버전 2로 저장한 데이터 디렉터리를 구버전 CLI와 동시에 사용하지 않는다. 변환 전에 실행 중인 작업을 정리하고 동일 디렉터리를 사용하는 CLI·서버·에이전트를 함께 갱신한다. 새 프로필 코드에서도 인증서 지문 변경 시 자동으로 다른 인증서를 선택하지 않는 기존 보호를 유지한다.

## 구현 순서와 검증

1. 버전 있는 구성 모델과 공통 접근 계층, 기존 형식 읽기·이행·호환 매핑을 먼저 구현한다.
2. 기관별 채널·인증 방법·용도·대상 확인·세션 충돌 범위를 어댑터 계약에 추가한다. 미구현 은행·채널은 준비 중으로 유지한다.
3. 대상이 명시된 API와 작업 스냅샷, 공유 세션 잠금, 버전·소속 검사를 구현한다.
4. 상단 프로필, 은행 통합 계좌·필터, 연결 설정, 작업별 대상 표시를 웹 화면에 연결한다.
5. 기존 업무 어댑터를 새 연결 모델에 하나씩 연결하고 CLI 호환을 검증한다.

완료 기준은 다음과 같다. 테스트는 가상 기관 응답과 로컬 전송 계층만 사용한다.

| 경우 | 확인할 결과 |
| --- | --- |
| 한 프로필의 여러 은행·동일 은행의 다른 채널 | 별도 연결로 선택·조회; 준비 중 채널은 UI·API 모두 실행 불가 |
| 여러 프로필에서 같은 인증서 사용 | 금고 자료는 한 번만 보관; 대상·세션·결과는 섞이지 않음 |
| 로그인과 계산서 발급용 인증서가 다름 | 용도별 수단 선택; 누락·만료 시 다른 수단으로 자동 대체하지 않음 |
| 한 기관 세션을 공유하는 두 사업장 동시 요청 | 대상 선택·확인·업무 실행 전체가 직렬화되고 각 결과의 사업장이 일치 |
| 개인 탭·법인 탭·자동화 동시 실행 | 전역 현재 프로필 없이 각 요청의 대상 유지 |
| 프로필 전환 뒤 늦게 도착한 응답 | 새 프로필의 화면·잔액에 섞이지 않음 |
| 초안 이후 화면 프로필만 전환 | 기존 작업 대상 유지; 원래 대상 표시 후 해당 작업 확인 가능 |
| 초안 이후 연결·인증 수단·사업장 설정 변경 | 재준비·재확인 요구; 이미 전송된 결과는 보존 |
| 서로 다른 대상에 같은 멱등 키 사용 | 충돌로 거절; 다른 대상 실행이나 결과 반환 없음 |
| 연결·계좌·문서의 소속 불일치 | 기관 요청·다운로드 전에 거절 |
| 일부 은행 조회 실패·미조회 | 은행별 상태·시각 보존; 미조회 잔액을 0원으로 합산하지 않음 |
| 기존 형식 읽기와 중단된 이행 | 자동 파일 변경·기관 접속 없음; 기존 인증서 선택과 설정 복구 가능 |

구현은 문서 작성과 별도 단계이며 실제 인증서 발급·로그인·이체·계산서 발급을 실행하지 않는다.
